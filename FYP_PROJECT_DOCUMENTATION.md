## 1. Project Overview

### Project Name
**AI-Powered Roommate Matching System**

### Purpose
A web-based application that uses Artificial Intelligence to match people looking for roommates. Instead of users manually browsing hundreds of profiles, the system automatically calculates how compatible two people would be as roommates — and explains *why* using natural language generated by Google's Gemini AI.

### Problem It Solves
Finding a compatible roommate is difficult because:
- People have different budgets, lifestyles, schedules, and habits
- Manual browsing is time-consuming and biased
- There is no scientific way to quantify "compatibility"
- Conflicts (e.g., one person smokes, the other doesn't) are only discovered after moving in

This system solves all of the above by:
- Automatically calculating compatibility scores between users
- Detecting potential conflicts **before** they become real problems
- Generating AI-powered explanations of why two people are (or aren't) a good match
- Providing room listings that match a user's preferences

### Key Features
| Feature | Description |
|---|---|
| AI Matching | 6-agent system calculates compatibility scores |
| Explainable AI | Gemini LLM explains match results in natural language |
| Conflict Detection | Identifies deal-breakers (pets, budget, noise) before they happen |
| Room Listings | Find rooms that match your preferences and budget |
| Preference Analysis | Converts human preferences into mathematical vectors |
| Survey Data | Pre-loaded with 327 real user profiles from survey data |
| JWT Authentication | Secure login with 30-day tokens |
| Audit Trail | Every AI decision is logged for transparency |

### File: `backend/database.py`

**Purpose:** Creates the SQLAlchemy database instance without initializing it.

**Why a separate file?** In Flask, if `app.py` creates the `db` object and `models/user.py` imports from `app.py`, you get a **circular import** (A imports B, B imports A). Keeping `db` in its own file breaks the cycle.

```python
from flask_sqlalchemy import SQLAlchemy
db = SQLAlchemy()
```

**How it works:**
- `db = SQLAlchemy()` creates an unbound instance
- Later, in `app.py`, `db.init_app(app)` binds it to the Flask app
- All models import `db` from this file

### File: `backend/app.py`

**Purpose:** The entry point of the entire backend. Uses the **Application Factory Pattern** to create and configure the Flask app.

#### Why Application Factory Pattern?

Without it:
```python
# bad: creates app at module level
app = Flask(__name__)
app.run()
```
This makes testing impossible because you can't create multiple apps with different configs.

With factory pattern:
```python
# good: create app on demand with any config
app = create_app('testing')
app = create_app('production')
```

#### `create_app(config_name)` — Step by Step

```python
def create_app(config_name=None):
    app = Flask(__name__)
    # Step 1: Create Flask instance

    app.config.from_object(get_config(config_name))
    # Step 2: Load config (dev/test/prod) settings into Flask

    db.init_app(app)
    # Step 3: Bind SQLAlchemy to this app (needed for database access)

    jwt.init_app(app)
    # Step 4: Initialize JWT token system

    CORS(app, origins="*", ...)
    # Step 5: Allow frontend (localhost:8000) to call backend (localhost:5000)
    # Without CORS, browsers block cross-origin HTTP calls

    _register_models(app)
    # Step 6: Import all models so SQLAlchemy knows which tables to create

    _register_routes(app)
    # Step 7: Register all URL blueprints (auth, users, preferences, etc.)

    _register_error_handlers(app)
    # Step 8: Register custom JSON error responses (404, 500, etc.)

    with app.app_context():
        db.create_all()
    # Step 9: Create all database tables (if they don't exist yet)

    return app
```

#### Blueprint Registration

### File: `backend/agents/base_agent.py`

**Purpose:** Defines the abstract base class that all 6 agents inherit from. Provides shared functionality: LLM access, callback tracking, audit logging, and tool registration.

#### Class: `AgentLoggingCallback`

This is a **LangChain callback handler** — it runs automatically whenever LangChain calls a tool or the LLM.

```python
class AgentLoggingCallback(BaseCallbackHandler):

    def on_tool_start(self, serialized, input_str, **kwargs):
        # Called automatically BEFORE a LangChain tool runs
        # Records: tool name, input, timestamp
        self.tool_calls.append({'tool': tool_name, 'input': input_str})

    def on_tool_end(self, output, **kwargs):
        # Called automatically AFTER a tool finishes
        # Records: output result

    def on_llm_start(self, serialized, prompts, **kwargs):
        # Called automatically BEFORE Gemini is invoked
        self.llm_calls.append({'model': 'gemini', 'timestamp': ...})

    def on_llm_end(self, response, **kwargs):
        # Called automatically AFTER Gemini responds
        # Records: finish time
```

This enables **Explainable AI (XAI)** — you can see exactly which tools ran and when Gemini was called.

#### Function: `get_llm(temperature=0.3)`

```python
def get_llm(temperature=0.3):
    api_key = os.getenv('GOOGLE_API_KEY', '')
    if not api_key:
        return None  # No API key → agents use rule-based fallback

    llm = ChatGoogleGenerativeAI(
        model='gemini-2.0-flash',
        google_api_key=api_key,
        temperature=0.3,
        # temperature: 0 = deterministic, 1 = creative
        # 0.3 = mostly consistent with slight variation
        max_output_tokens=2048,
        timeout=15,
        max_retries=1,
    )
    return llm
```

**temperature=0.3 explanation:** At 0, Gemini always gives the same answer. At 1, it's creative but inconsistent. 0.3 means answers are mostly consistent but not robotic — ideal for scoring explanations.

#### Abstract Base Class: `BaseAgent`

```python
class BaseAgent(ABC):
    # Singleton LLM shared by all 6 agents
    _shared_llm = None
    _llm_initialized = False

    def __init__(self, agent_name, version, system_prompt):
        # Initialize shared LLM only once (expensive operation)
        if not BaseAgent._llm_initialized:
            BaseAgent._shared_llm = get_llm()
            BaseAgent._llm_initialized = True
        self.llm = BaseAgent._shared_llm

        # Register this agent's LangChain tools
        self.tools = self._register_tools()

    @abstractmethod
    def _register_tools(self):
        # Must be implemented by each agent
        # Returns a list of LangChain @tool functions

    @abstractmethod
    def execute(self, **inputs):
        # Must be implemented by each agent
        # Returns AgentResult
```

#### Key Methods

**`invoke_llm(user_prompt)`** — sends a question to Gemini and returns text:
```python
def invoke_llm(self, user_prompt, system_prompt=None):
    messages = [
        SystemMessage(content=self.system_prompt),  # Role definition
        HumanMessage(content=user_prompt)            # The actual question
    ]
    response = self.llm.invoke(messages, config={"callbacks": [self.callback_handler]})
    return response.content  # Text response from Gemini
```

**`invoke_llm_json(user_prompt)`** — same but parses response as JSON:
```python
def invoke_llm_json(self, user_prompt):
    raw = self.invoke_llm(user_prompt)
    # Gemini sometimes wraps JSON in ```json ... ``` markdown blocks
    cleaned = raw.strip().removeprefix('```json').removesuffix('```')
    return json.loads(cleaned)
```

**`create_chain(prompt_template)`** — builds a LangChain pipeline:
```python
def create_chain(self, prompt_template, output_parser=None):
    parser = output_parser or StrOutputParser()
    return prompt_template | self.llm | parser
    # The | operator chains: prompt → llm → parser
    # This is LangChain's LCEL (LangChain Expression Language) syntax
```

**`log_decision(entity_type, entity_id, action, details)`** — writes to audit log:

```python
def log_decision(self, entity_type, entity_id, action, details):
```

```python
def _register_agents(self):

        UserProfilingAgent(),
        PreferenceAnalysisAgent(),
        CompatibilityScoringAgent(),
        RoomMatchingAgent(),
        ConflictDetectionAgent(),
```

#### Pipeline: `find_matches_for_user(user_id, min_score=60)`

This is the **most important method** in the entire system. When a user clicks "Find Matches", this runs:

```
Step 1: User Profiling Agent
    → Validate user exists and profile is complete
    → If FAILS: abort entire pipeline

Step 2: Preference Analysis Agent
    → Load user's preferences
    → Convert to 6-dimensional NumPy vector
    → Save vector to database

Step 2.5: Vectorize all OTHER users (up to 50)
    → For each other user, run Preference Analysis Agent
    → Skip if their vector already exists and is fresh (<30 days old)

Step 3: Compatibility Scoring Agent (for each candidate)
    → Load both users' preference vectors
    → Compute cosine similarity
    → Compute lifestyle, schedule, budget, habits scores
    → Apply weighted formula to get overall score
    → Save score to database

Step 3.5: Conflict Detection Agent (for each candidate)
    → Check pets, smoking, budget, noise conflicts
    → Label each as Hard (deal-breaker) or Soft (warning)
    → Save to database

Step 4: Recommendation Engine Agent
    → Load all scores from database
    → Filter: min_score AND no hard conflicts
    → Rank by score (highest first)
    → Generate AI explanation for each match (Gemini)
    → Return top 20 recommendations

→ Generate pipeline summary via Gemini (optional)
→ Return complete results
```

#### Pipeline: `find_rooms_for_user(user_id, limit=20)`

```
Step 1: User Profiling Agent → Validate user
Step 2: Room Matching Agent → Filter rooms by preferences
Step 3: Conflict Detection Agent → Check user-room conflicts
```

#### `execute_agent(agent_name, **inputs)`

Every agent is called through this method, which wraps execution with timing and logging:

```python
def execute_agent(self, agent_name, **inputs):
    agent = self.agents[agent_name]
    start_time = datetime.utcnow()

    result = agent.execute(**inputs)  # Run the actual agent

    duration = (datetime.utcnow() - start_time).total_seconds() * 1000
    self.execution_log.append({
        'agent': agent_name,
        'status': result.status.value,
        'duration_ms': duration,
        ...
    })
    return result
```

#### Singleton Pattern

```python
_orchestrator_instance = None

def get_orchestrator():
    global _orchestrator_instance
    if _orchestrator_instance is None:
        _orchestrator_instance = AgentOrchestrator()
    return _orchestrator_instance
```

**Why singleton?** Creating 6 agents and initializing the LLM is expensive. The singleton ensures this happens only once, no matter how many API requests come in.

### File: `backend/agents/user_profiling_agent.py` — Agent 1/6

**Purpose:** Validates a user's profile and checks if it's complete enough to be used in matching.

#### LangChain Tools Registered:
- `validate_email(email)` — checks email format
- `check_duplicate(email)` — checks if email already exists in DB
- `compute_completeness(user_id)` — calculates profile completeness %

#### `execute(user_id)` Logic:
1. Load user from database
2. Check if user exists and is active
3. Check if user has set preferences
4. Compute profile completeness (required fields + optional fields)
5. Invoke Gemini to generate a profile analysis description
6. Return AgentResult with completeness score and profile status

#### Profile Completeness Scoring:

### File: `backend/agents/preference_analysis_agent.py` — Agent 2/6

**Purpose:** Converts a user's raw preferences into a 6-dimensional numerical vector for mathematical comparison.

#### Why Vectorize Preferences?

You cannot directly compare "I prefer Clean" with "I prefer Very Clean". But you CAN compare `[0.7]` with `[1.0]`. Vectorization converts human preferences into numbers that math can work with.

#### The 6-Dimensional Preference Vector

```python
vector = [
    budget_norm,       # budget_min normalized to 0-1 scale
    age_norm,          # preferred age (middle of range) normalized
    noise_norm,        # noise_tolerance / 10
    smoking_norm,      # 1.0 if smoking_ok=True, 0.0 if False
    pets_norm,         # 1.0 if pets_ok=True, 0.0 if False
    cleanliness_norm   # {'Very Clean':1.0, 'Clean':0.7, 'Average':0.5, 'Relaxed':0.2}
]
```

#### Normalization Example:
```
User's budget_min = $500
Max possible budget = $5000

budget_norm = 500 / 5000 = 0.1

User's noise_tolerance = 7 out of 10
noise_norm = 7 / 10 = 0.7
```

After normalization, all values are between 0 and 1, making them comparable.

#### LangChain Tools:
- `vectorize_preferences(user_id)` — creates the vector
- `compute_similarity(vec_a, vec_b)` — cosine similarity between two vectors

#### Gemini Analysis:
After vectorizing, the agent sends the vector to Gemini to identify the user's "preference type":
- **Budget-conscious**: low budget_norm
- **Social butterfly**: high noise_norm, smoking_ok or pets_ok
- **Quiet studious**: low noise_norm, high cleanliness_norm
- **Flexible**: middle values across all dimensions

### File: `backend/agents/compatibility_scoring_agent.py` — Agent 3/6

**Purpose:** Computes a compatibility score (0-100) between two users using their preference vectors and additional heuristic scoring.

#### The Scoring Formula

```
overall_score = (cosine_similarity × 0.30 × 100)
              + (lifestyle_score    × 0.20)
              + (schedule_score     × 0.20)
              + (budget_score       × 0.15)
              + (habits_score       × 0.15)
```

Each component is scored 0-100, then weighted and summed.

#### Component 1: Cosine Similarity (30%)

**What is cosine similarity?**

Imagine each user's preferences as a point in 6-dimensional space. Cosine similarity measures the angle between the two vectors pointing to those points.

- **Angle = 0°** → vectors point same direction → similarity = 1.0 (100% similar)
- **Angle = 90°** → vectors are perpendicular → similarity = 0.0 (completely different)

```python
def _cosine_similarity(self, vector_a, vector_b):
    vec_a = np.array(vector_a.vector_data)
    vec_b = np.array(vector_b.vector_data)

    dot_product = np.dot(vec_a, vec_b)
    # dot product = sum of element-wise products

    norm_a = np.linalg.norm(vec_a)
    norm_b = np.linalg.norm(vec_b)
    # norm = length (magnitude) of vector = √(x₁² + x₂² + ... + xₙ²)

    similarity = dot_product / (norm_a * norm_b)
    # cosine similarity formula
    return float(np.clip(similarity, 0, 1))
    # clip to [0,1] because negative cosine similarity doesn't make practical sense
```

#### Component 2: Lifestyle Score (20%)

```python
CLEANLINESS_MAP = {'Very Clean': 10, 'Clean': 7, 'Average': 5, 'Relaxed': 2}

def _estimate_lifestyle_score(self, user_a, user_b):
    score = 50  # base score
    
    if user_a.city == user_b.city:
        score += 20  # Same city = significant compatibility bonus
    
    clean_gap = abs(CLEANLINESS_MAP[prefs_a.cleanliness_level] 
                  - CLEANLINESS_MAP[prefs_b.cleanliness_level])
    if clean_gap == 0:
        score += 20  # Perfect cleanliness match
    elif clean_gap <= 2:
        score += 15
    elif clean_gap <= 4:
        score += 8
    
    noise_gap = abs(prefs_a.noise_tolerance - prefs_b.noise_tolerance)
    if noise_gap <= 2:
        score += 10
    elif noise_gap <= 4:
        score += 5
    
    return min(100, max(0, score))
```

#### Component 3: Schedule Compatibility Matrix (20%)

```python
SCHEDULE_COMPAT = {
    ('9-5 Job', '9-5 Job'): 95,      # Both work 9-5 → great match
    ('Night Shift', 'Night Shift'): 95,
    ('Student', 'Student'): 90,
    ('9-5 Job', 'Night Shift'): 30,   # Opposite schedules → barely compatible
    ('Student', 'Night Shift'): 45,
    ('Flexible', 'Flexible'): 85,
    ...
}
```

A 9-5 worker and a night shift worker have a score of 30 because one sleeps when the other is active — they'd constantly disturb each other.

#### Component 4: Budget Compatibility (15%)

```python
def _estimate_budget_score(self, user_a, user_b):
    # Find the overlapping budget range
    overlap_min = max(a_min, b_min)  # Start of overlap
    overlap_max = min(a_max, b_max)  # End of overlap

    if overlap_min > overlap_max:
        return 20  # No overlap at all → very low score

    overlap_percent = overlap_range / smaller_range
    return int(40 + (overlap_percent * 60))
    # More overlap → higher score
    # Max 100 if ranges are identical
```

#### Component 5: Habits Score (15%)

```python
def _estimate_habits_score(self, user_a, user_b):
    score = 100
    if prefs_a.smoking_ok != prefs_b.smoking_ok:
        score -= 35   # Smoking mismatch: major penalty
    if prefs_a.pets_ok != prefs_b.pets_ok:
        score -= 25   # Pets mismatch: significant penalty
    if abs(clean_a - clean_b) >= 5:
        score -= 20   # Large cleanliness gap
    return max(0, score)
```

```javascript
class APIClient {
    constructor() {
        this.baseURL = 'http://localhost:5000';
    }

    getToken() {
        return localStorage.getItem('access_token');
        // JWT token stored in browser localStorage
    }

    async request(method, endpoint, data = null) {
        const headers = { 'Content-Type': 'application/json' };
        const token = this.getToken();
        if (token) {
            headers['Authorization'] = `Bearer ${token}`;
            // Attach JWT to every request that needs auth
        }
        const response = await fetch(this.baseURL + endpoint, {
            method, headers,
            body: data ? JSON.stringify(data) : null
        });
        return await response.json();
    }
```

## 6. Core Algorithms

### Algorithm 1: Cosine Similarity

**Used for:** Comparing two users' preference vectors (30% of compatibility score)

**Mathematical formula:**
```
similarity(A, B) = (A · B) / (||A|| × ||B||)

where:
  A · B = dot product = A[0]×B[0] + A[1]×B[1] + ... + A[n]×B[n]
  ||A|| = vector norm = √(A[0]² + A[1]² + ... + A[n]²)
```

**Concrete example:**
```
User A vector: [0.1, 0.8, 0.7, 0.0, 1.0, 0.5]  (budget-sensitive, clean, no smoking)
User B vector: [0.2, 0.7, 0.6, 0.0, 1.0, 0.7]  (similar profile)

dot product = (0.1×0.2) + (0.8×0.7) + (0.7×0.6) + (0.0×0.0) + (1.0×1.0) + (0.5×0.7)
           = 0.02 + 0.56 + 0.42 + 0.00 + 1.00 + 0.35
           = 2.35

||A|| = √(0.01 + 0.64 + 0.49 + 0 + 1 + 0.25) = √2.39 = 1.546
||B|| = √(0.04 + 0.49 + 0.36 + 0 + 1 + 0.49) = √2.38 = 1.543

similarity = 2.35 / (1.546 × 1.543) = 2.35 / 2.385 = 0.985

Final cosine score = 0.985 × 100 × 0.30 = 29.55 points (out of 30 maximum)
```

**Why cosine and not Euclidean distance?**

Euclidean distance measures absolute difference. Cosine similarity measures direction. Two users can have different absolute budgets but the same relative preferences — cosine handles this better.

### Algorithm 2: Weighted Score Aggregation

```
Total Score = Σ (component_score × weight)

= (cosine_sim × 100 × 0.30)     → max 30 points
+ (lifestyle_score × 0.20)       → max 20 points
+ (schedule_score × 0.20)        → max 20 points
+ (budget_score × 0.15)          → max 15 points
+ (habits_score × 0.15)          → max 15 points
                                 = max 100 points total
```

**Why these weights?**
- Cosine similarity (30%) captures the overall preference pattern
- Lifestyle (20%) captures day-to-day living habits
- Schedule (20%) prevents the major "one sleeps while other is awake" problem
- Budget (15%) is important but flexible with the right roommate
- Habits (15%) covers the hard deals (smoking, pets)

### Algorithm 3: Preference Vectorization

```
Input:  UserPreference object (budget, cleanliness, noise_tolerance, etc.)
Output: 6-dimensional numpy array [0-1 values]

budget_norm     = budget_min / 5000        (normalize to max $5000)
age_norm        = (age_min + age_max) / 2 / 65  (midpoint of preferred age range)
noise_norm      = noise_tolerance / 10
smoking_norm    = 1.0 if smoking_ok else 0.0
pets_norm       = 1.0 if pets_ok else 0.0
cleanliness_norm = cleanliness_map[level]  {'Very Clean':1.0, 'Clean':0.7, 'Average':0.5, 'Relaxed':0.2}
```

### Algorithm 4: Budget Overlap

```
User A: $300 - $700
User B: $500 - $1000

Overlap start = max(300, 500) = 500
Overlap end   = min(700, 1000) = 700
Overlap range = 700 - 500 = 200

A_range = 700 - 300 = 400
B_range = 1000 - 500 = 500

Overlap percent = min(200/400, 200/500) = min(0.5, 0.4) = 0.4

Budget score = 40 + (0.4 × 60) = 40 + 24 = 64 / 100
```

If ranges don't overlap at all → score = 20 (minimum, not 0)

## 10. Key Features Explained

### Feature 1: Multi-Agent Architecture

The system uses **6 specialized AI agents** instead of one monolithic function. This is better because:

- Each agent does one job well (**Single Responsibility Principle**)
- Agents can be upgraded independently
- If one agent fails, the pipeline continues (graceful degradation)
- The orchestrator can skip or retry individual agents
- Each agent has its own LangChain tools, prompt templates, and Gemini chains

### Feature 2: LangChain Integration

LangChain provides:

**Tools:** Python functions wrapped with `@tool` decorator that agents can "use":
```python
@tool
def compute_cosine_similarity(vector_a_json: str, vector_b_json: str) -> str:
    """Compute cosine similarity between two preference vectors."""
    # ... numpy math ...
```

**Chains (LCEL):** The pipe `|` operator chains components:
```python
chain = prompt_template | llm | output_parser
result = chain.invoke({"key": "value"})
# Prompt is formatted → sent to Gemini → output parsed
```

**Callback Handlers:** Automatically called during execution:
```python
class AgentLoggingCallback(BaseCallbackHandler):
    def on_tool_start(self, ...):  # before tool runs
    def on_llm_start(self, ...):   # before Gemini is called
```

### Feature 3: Explainable AI (XAI)

Every recommendation includes:
1. **Numerical breakdown:** lifestyle=85, schedule=70, budget=60, habits=90
2. **AI explanation:** "Alice and Bob would make excellent roommates. Both prefer clean environments and work traditional hours, making their daily schedules naturally compatible..."
3. **Conflict warnings:** "Note: Bob allows pets while Alice prefers no pets"
4. **Audit trail:** Every agent decision is stored in `audit_logs` table

This makes the system transparent — users know **why** they matched with someone, not just that they did.

### Feature 4: Graceful Degradation

If the Google API key is not set or Gemini is unavailable:
```python
def get_llm():
    api_key = os.getenv('GOOGLE_API_KEY', '')
    if not api_key:
        return None  # No crash — return None

class BaseAgent:
    def invoke_llm(self, prompt):
        if not self.llm:
            return None  # No crash — return None
```

Each agent has a fallback:
```python
ai_interpretation = None
if self.interpretation_chain:
    ai_interpretation = self.interpretation_chain.invoke(...)  # Try Gemini

if not ai_interpretation:
    ai_interpretation = self._fallback_interpretation(...)  # Use rule-based
```

The system works without Gemini — scores are still computed, explanations are template-based.

### Feature 5: Score Caching

Computing cosine similarity for 50 users × 50 users = 2500 computations. This would be slow.

**Solution:** Cache results in the database:
```python
# Check cache first
cached_score = CompatibilityScore.query.filter(...).first()
if cached_score and not cached_score.is_stale():
    return cached_score  # Return cached result instantly

# Only recompute if cache is stale (>7 days)
```

## 12. Security Considerations

### 1. Password Security

```python
# Store: bcrypt hash (irreversible)
self.password_hash = bcrypt.hashpw(password.encode('utf-8'), bcrypt.gensalt(rounds=10))

# Never store: plain text password
# Never compare: plain text passwords
# Always compare: bcrypt.checkpw(provided, stored_hash)
```

**bcrypt facts:**
- The hash includes a random `salt` — even if two users have the same password, their hashes are different
- `rounds=10` means 2^10 = 1024 iterations of hashing, making brute force very slow (~0.1 second per attempt)
- Even if the database is stolen, attackers cannot easily recover passwords

### 2. JWT Token Security

```python
JWT_SECRET_KEY = os.getenv('JWT_SECRET_KEY', 'dev-key')
```

### General Questions

**Q1: What problem does your project solve?**
> Finding a compatible roommate is a significant challenge, especially for students and young professionals. The traditional approach — posting listings on Facebook or bulletin boards and hoping for the best — is inefficient and often results in incompatible living situations. Our system automates this process using AI, mathematically quantifying compatibility across 5 dimensions (budget, lifestyle, schedule, habits, overall preference similarity) and using Google's Gemini LLM to explain the results in plain English. Users get ranked matches with transparent explanations, not just a black-box score.

**Q2: What makes this an AI project?**
> The project uses multiple forms of AI:
> 1. **LangChain multi-agent architecture** — 6 specialized AI agents that each handle one part of the problem
> 2. **Google Gemini LLM** — generates natural language explanations for why two people are compatible
> 3. **Cosine similarity** — a machine learning technique borrowed from NLP (where it's used to compare document vectors) applied to preference vectors
> 4. **Explainable AI (XAI)** — every decision is logged and can be traced back, unlike a black-box model
> 5. **Rule-based AI fallback** — the system degrades gracefully if the LLM is unavailable

**Q3: Why did you choose LangChain?**
> LangChain provides a structured framework for building AI applications. Without it, we'd need to manually manage prompt formatting, LLM API calls, output parsing, and tool invocation. LangChain's LCEL (LangChain Expression Language) lets us compose these into clean pipelines: `prompt | llm | output_parser`. It also provides standardized callback handlers for monitoring, which is critical for our Explainable AI requirements.

### Technical Questions

**Q4: What is cosine similarity and why did you use it?**
> Cosine similarity measures the angle between two vectors in n-dimensional space. If the angle is 0°, the vectors point in the same direction (similarity = 1.0, perfect match). If the angle is 90°, they're perpendicular (similarity = 0, no match). We convert each user's preferences into a 6-dimensional vector (budget, age, noise, smoking, pets, cleanliness — all normalized to 0-1) and compute cosine similarity between them.
>
> We chose cosine over Euclidean distance because cosine ignores magnitude and focuses on direction. Two users with different absolute budgets but similar relative preferences will still score high — which is the right behavior.

**Q5: How does your vectorization work?**
> Each user's preferences are converted to a 6-dimensional NumPy array:
> - `budget_norm` = budget_min / 5000 (max budget)
> - `noise_norm` = noise_tolerance / 10
> - `smoking_norm` = 1.0 if smoking_ok else 0.0
> - `pets_norm` = 1.0 if pets_ok else 0.0
> - `cleanliness_norm` = {Very Clean: 1.0, Clean: 0.7, Average: 0.5, Relaxed: 0.2}
> - `age_norm` = midpoint of preferred age range / 65
>
> All values are normalized to [0, 1] so no single dimension dominates the similarity calculation.

**Q6: How is the overall compatibility score calculated?**
> ```
> score = cosine_similarity × 100 × 0.30
>       + lifestyle_score × 0.20
>       + schedule_score × 0.20
>       + budget_score × 0.15
>       + habits_score × 0.15
> ```
> Cosine gets the highest weight (30%) because it captures the overall preference pattern. Schedule gets 20% because incompatible schedules (day worker vs. night shift) are a major real-world source of roommate conflict. Budget gets 15% because while important, a slight mismatch can be negotiated.

**Q7: What is the difference between hard and soft conflicts?**
> **Hard conflicts** are deal-breakers that should prevent a match. For example: User A doesn't accept pets but User B has a cat (severity 9/10), or their budget ranges don't overlap at all (severity 8/10). These pairs are filtered out of recommendations entirely.
>
> **Soft conflicts** are warnings — things to discuss but not immediate deal-breakers. For example: different schedules, slight cleanliness preference gap, gender preference mismatch. These are shown as warnings on the match card but don't block the recommendation.

**Q8: Why a multi-agent architecture instead of one function?**
> Single Responsibility Principle — each agent does one job and does it well. Benefits:
> 1. Each agent can be improved independently (we can upgrade the scoring algorithm without touching the profiling agent)
> 2. Easier debugging — if a match is wrong, you know which agent caused it
> 3. Each agent has its own LangChain tools, prompt, and Gemini chain optimized for its task
> 4. Graceful degradation — if one agent fails, others continue
> 5. Observable — the orchestrator logs every agent's execution time and success rate

**Q9: How does JWT authentication work?**
> 1. User sends email + password to `POST /auth/login`
> 2. Backend verifies password with bcrypt
> 3. Backend creates a JWT: `create_access_token(identity=str(user_id), expires=30days)`
> 4. JWT is a base64-encoded string: `header.payload.signature` — the signature uses the server's `JWT_SECRET_KEY` to prove it's authentic
> 5. Frontend stores the JWT in `localStorage`
> 6. Every subsequent request includes `Authorization: Bearer <token>`
> 7. Flask's `@jwt_required()` decorator automatically validates the token before the function runs
> 8. `get_jwt_identity()` extracts the user_id from the verified token

**Q10: Why SQLite for development and PostgreSQL for production?**
> SQLite is a file-based database — no server needed, zero configuration, great for development. PostgreSQL is a production-grade database that supports concurrent connections, better performance under load, and more SQL features. The abstraction through SQLAlchemy ORM means we can switch between them just by changing one environment variable (`DATABASE_URL`).

**Q11: What does `db.session.rollback()` do and when is it called?**
> When SQLAlchemy writes to the database, it does so within a transaction. If an error occurs midway through multiple writes, without rollback, the database could be left in a partial/corrupt state. `db.session.rollback()` undoes all changes since the last commit. We call it in every exception handler: `except Exception: db.session.rollback()`.

**Q12: How does bcrypt salt work?**
> When hashing a password, bcrypt generates a random 16-byte "salt" and combines it with the password before hashing. The salt is stored as part of the hash string itself. When verifying: `bcrypt.checkpw(provided_password, stored_hash)` extracts the salt from the stored hash, applies it to the provided password, and compares. This means:
> - The same password always produces a different hash (because different salt each time)
> - Attacker cannot use pre-computed rainbow tables
> - The salt doesn't need to be stored separately

### Architecture Questions

**Q13: Explain the Application Factory Pattern.**
> Instead of creating the Flask app at module level (`app = Flask(__name__)`), we wrap it in a `create_app(config_name)` function. This pattern allows:
> - Creating multiple app instances with different configurations (e.g., one for testing with SQLite in-memory, one for production with PostgreSQL)
> - Testing without actually starting a server
> - Avoiding circular imports (models can import `db` from `database.py` without importing `app.py`)

**Q14: What is the Singleton pattern and where is it used?**
> The Singleton pattern ensures only one instance of a class exists. We use it for:
> 1. The `AgentOrchestrator` — creating 6 agents and initializing Gemini is expensive. The singleton ensures this happens once: `_orchestrator_instance = None; def get_orchestrator(): if not _orchestrator_instance: create...; return _orchestrator_instance`
> 2. The LLM — `BaseAgent._shared_llm` is a class variable shared across all 6 agents. One API connection instead of six.

**Q15: How does the preference vector become stale and what happens?**
> Each `PreferenceVector` record has a `computed_at` timestamp. `is_stale(max_age_days=30)` checks if more than 30 days have passed. If a user updates their preferences, their vector is recomputed on the next matching pipeline run (Step 2.5 of `find_matches_for_user`). If the vector is fresh, it's reused, saving computation time.

**Q16: What is LCEL (LangChain Expression Language)?**
> LCEL is LangChain's syntax for composing components using the `|` (pipe) operator:
> ```python
> chain = prompt_template | llm | output_parser
> result = chain.invoke({"variables": "values"})
> ```
> This is analogous to Unix pipes (`cat file | grep pattern | sort`). Each component transforms the data and passes it to the next. The prompt is formatted with variables → sent to Gemini → response is parsed and returned.

### Design Decisions

**Q17: Why not use a framework like React for the frontend?**
> The project scope prioritized the AI backend and multi-agent system as the core contribution. Using vanilla HTML/CSS/JavaScript kept the frontend simple and avoided dependency management complexity. The `APIClient` class in `api.js` provides clean abstraction of all HTTP calls, which achieves the same separation of concerns as a framework without the overhead.

**Q18: Why store preferences in the database and not just recompute them each time?**
> Storing computed vectors (in `preference_vectors` table) is an optimization called **caching**. Computing a cosine similarity for 50 users × 50 users = 2,500 computations per match request. With caching, if nothing changed, we reuse the stored results. The `is_stale()` method ensures stale data is refreshed. This reduces response time significantly.

**Q19: How does the system handle a new user with no matches?**
> The system handles this gracefully:
> 1. `find_matches_for_user()` runs Step 2.5 which vectorizes all other users
> 2. Step 3 computes scores against all other users (not just mutual matching)
> 3. If no scores are above `min_score=60`, the recommendation engine returns an empty list
> 4. The API returns `{recommendations: [], count: 0, success: true}` — not an error
> 5. The frontend displays "No matches found, try adjusting your preferences"

### LangChain / AI Specific

**Q21: What is a LangChain "Tool" and how is it different from a regular function?**
> A LangChain `@tool` is a Python function decorated to be callable by an AI agent. The difference:
> - Regular function: called explicitly by name in code
> - LangChain Tool: registered with the agent, has a docstring describing its purpose, and can be invoked either explicitly in code (as we do) or potentially by an LLM agent that decides which tool to use based on the task
>
> Our agents use tools explicitly (we call them in order), but the `@tool` decorator provides standardized logging, error handling, and callback integration through LangChain's framework.

**Q22: Why temperature=0.3 for Gemini?**
> Temperature controls randomness in LLM outputs. 0.0 = fully deterministic (same input → same output every time). 1.0 = highly creative but potentially inconsistent. We chose 0.3 because compatibility explanations should be consistent and professional, but not robotically identical for every user. Slight variation at 0.3 makes explanations feel more natural.

**Q23: What happens if the Gemini API is down?**
> Every agent has a `_fallback_*` method:
> ```python
> ai_interpretation = None
> if self.interpretation_chain:
>     ai_interpretation = self.interpretation_chain.invoke(...)
> 
> if not ai_interpretation:
>     ai_interpretation = self._fallback_interpretation(overall, cosine, ...)
> ```
> The fallback uses template-based strings: "Strong compatibility at {score}%. These users share very similar preferences in {strongest_area}." The scores are still computed (purely numerical, no LLM needed). The system degrades gracefully — users still get matches and scores, just without AI-generated narrative explanations.

**Q24: How does the audit log support Explainable AI?**
> Every `agent.log_decision()` call records:
> - Which agent made the decision
> - What action was taken
> - The entity affected (user ID, score ID, etc.)
> - Full details including all computed scores and the LangChain execution trace (which tools ran, how many LLM calls were made)
>
> This means for any recommendation, you can trace the complete decision path: "The Compatibility Scoring Agent ran 3 tools, called Gemini once, scored 82/100 because lifestyle=90, schedule=75, budget=60, habits=95". This is the definition of Explainable AI — transparent, auditable reasoning.
